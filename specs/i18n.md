# Internationalization Specification — Angular Lab

How the platform presents itself in more than one language. Complements
`specs/product.md` (what the product is) and `specs/missions.md` (the
mission/step model itself, as opposed to its translated text).

## Supported Languages

- English (`en`) — default and fallback.
- Spanish (`es`).
- Ukrainian (`uk`).

Adding a language means adding a UI-chrome JSON file and, optionally, a
mission-content overlay file; no code changes are required beyond registering
the new code in `LANGUAGES` (`src/app/core/services/language.service.ts`).

## Scope

- **In scope:** all app chrome (navigation, buttons, forms, auth flows, the
  dashboard, mission UI shell, empty states, toasts, confirmation dialogs) —
  **and all mission content** (title, description, goal, step prose, hints,
  checkpoint questions/options/explanations, comparisons — see *Mission
  content translation* below). **No learner-facing text lives in a `.ts` file
  anywhere in the app, including English** — every string, in every language,
  lives in a JSON file. `src/content/missions/*.ts` holds only structural data
  (step ids/types, checkpoint `correctIndex`, difficulty, duration, tags,
  `starterCode`) — see `MissionMeta` in `mission.model.ts`.
- **Out of scope, deliberately:**
  - **Track names** (`Mission.track`, e.g. "Fundamentals") — free-form catalog
    strings, not a fixed enum, so they're treated as structural metadata
    rather than translatable prose (unlike `difficulty`, which is a 3-value
    enum and *is* translated via `mission.header.difficulty.*`).
  - **`starterCode`** — it's code, not language-dependent.
  - **Server-driven error messages** (auth API responses surfaced via
    `AuthService`) — these originate on the backend in English; localizing them
    would mean localizing the Functions layer too, which is a separate change.
  - **Page `<title>` / meta description tags** (`routeMeta`) — stay English
    regardless of the active UI language. Making these locale-aware would
    require prefixed routes for SEO/hreflang, which is exactly the
    architecture this spec avoids (see *Why not Analog's built-in i18n*).
    Mechanically they're resolved the same way as everything else — an async
    `ResolveFn` reading `MissionTranslationService.getEnglishSummary()`, which
    always reads the English text regardless of `LanguageService.lang()`.
  - **The completion-card SVG's own baked-in labels**
    (`core/achievements/share-card.ts`) — this artifact is designed to leave
    the app (Decision 15, `context.md`) with a fixed visual identity; its
    *own* literal strings stay English for the same reason its theme doesn't
    follow the viewer. The mission title it displays as *data* does localize
    (it flows through the same hydrated `Mission` object as everywhere else)
    — only the SVG's own hardcoded chrome text is excluded.

## Why not Analog's built-in i18n

Analog wraps Angular's `$localize` (`provideI18n()`), which resolves strings at
template-compile time. On a static build it detects locale from the first URL
segment (`/es/...`) and switching languages means **navigating to a different
locale-prefixed route** — already-rendered components do not react to a runtime
translation change. That would have required prefixing every existing route and
touching the SEO/sitemap script and E2E suite.

`ngx-translate` gives a reactive `| translate` pipe (Angular-signals-backed as
of v18, zoneless-compatible) that updates text in place with no navigation —
the same UX as the existing dark/light `ThemeService` toggle.

## Behavior

- **Switching is instant.** Picking a language in the header selector
  (`app-language-switcher`) re-renders all currently-visible chrome text with no
  page reload or route change.
- **The choice persists** in `localStorage` (`angular-lab:lang`), read on next
  visit by `LanguageService.getInitialLang()` — same pattern as `ThemeService`
  and its `angular-lab:theme` key.
- **Missing keys fall back to English** (`fallbackLang: 'en'`), never to a raw
  translation key, so a partially-translated future addition degrades
  gracefully instead of showing `mission.someNewKey`.
- **Language names are shown untranslated, in their own language** (endonyms:
  "English", "Español", "Українська") — a learner should be able to find their
  language even if they can't read whichever language is currently active.

## Where UI-chrome translations live

- `public/i18n/{en,es,uk}.json` — served statically at `/i18n/{lang}.json`
  (same mechanism as `public/vertex-editor/*.js`), fetched by
  `@ngx-translate/http-loader` on language change. Fetched eagerly on every
  page load (`provideAppInitializer` blocks first render on it) since it's
  small (chrome copy only) and every page needs it.
- Keys are namespaced to mirror the component tree (`nav.*`, `auth.login.*`,
  `dashboard.settings.*`, `mission.*`, `common.*` for text repeated across
  unrelated features). All three files carry the exact same key set — verified
  by comparing them, not by convention.
- English values in `en.json` are the source of truth for existing UI copy:
  they're verbatim copies of what shipped before this spec, so unit/E2E
  assertions that check rendered English text keep passing unmodified.

## Mission content translation

Mission content (~1500 lines of prose across 12 missions) is split into two
layers, and translated **separately** from UI chrome for a load-order reason:
bundling it into `public/i18n/{lang}.json` would mean fetching all of it on
every page, including the home page, before first render.

**The two layers:**

- **Structural data** (`src/content/missions/*.ts`, typed as `MissionMeta` in
  `mission.model.ts`) — everything about a mission that ISN'T text: `id`,
  `difficulty`, `durationMinutes`, `track`, `tags`, `prerequisites`,
  `previewMode`, `starterCode`, and each step's `id`/`type` plus (for
  checkpoint steps) each checkpoint's `correctIndex`. No `title`, `content`,
  `hint`, `description`, `goal`, checkpoint `question`/`options`/
  `explanation`, or `comparison` object appears anywhere in these files.
- **Text** (`public/i18n/missions/{en,es,uk}.json`) — every mission's `title`,
  `description`, `goal`, and `steps` (keyed by step `id`, holding
  `title`/`content`/`hint`/`checkpoints`/`comparison`), **for every language
  including English.** `en.json` is the *required* base — there is nowhere
  further to fall back to, so it must have complete coverage (enforced by
  `src/content/missions/translations.spec.ts`); `es.json`/`uk.json` are
  partial overlays that fall back to English field-by-field.

**Loading:** `MissionTranslationService`
(`src/app/core/services/mission-translation.service.ts`) fetches
`en.json` **once, eagerly**, the moment it's first injected (i.e. the moment a
learner visits `/missions`, `/mission/[id]`, or the dashboard progress tab) —
it's the required base and `routeMeta` needs it too, so there's no English
fallback to lazy-load *from*. Non-English overlays are still fetched lazily,
only on an actual language switch, exactly like UI chrome.

- `ready()` is `false` until English has loaded; consuming pages show a
  `common.loading` message during that (typically sub-second) window rather
  than flashing an empty catalog or a false "not found".
- **`hydrate(meta)` assembles the full `Mission`** components render, merging
  structural `MissionMeta` with English text and (if active) the language
  overlay, falling back field-by-field to English — the same
  graceful-degradation principle as UI-chrome's `fallbackLang`.
- **Hydrating happens at the page/tab level**
  (`missions.page.ts`, `mission/[id].page.ts`, `dashboard/progress-tab.ts`),
  not inside `MissionCatalogService` or `MissionStateService` — those stay
  structural-only internally (progress tracking and code-per-step storage key
  off step `id`s, which don't change across languages). The already-hydrated
  `Mission` is then passed down through existing component inputs
  (`MissionHeader`, `MissionNav`, `MissionStep`, `MissionCard`,
  `MissionCompleted`, …), so none of those presentational components needed
  to change — they already just render whatever `Mission` shape they're
  given.
- **`routeMeta`'s title/meta resolve asynchronously** via
  `MissionTranslationService.getEnglishSummary(id)` (an `Observable`, which
  Angular's `ResolveFn` supports natively) — this reads the same cached
  `en.json` fetch the rest of the page uses, so visiting a mission page
  directly doesn't trigger a second request.
- **Checkpoint `options` and comparison `points` are matched positionally.**
  `CheckpointMeta.correctIndex` is a number pointing into the `options` array
  and lives in the *structural* layer, not any translation file, so a
  translated `options` array shorter than `correctIndex` — or reordered
  relative to English — would silently make the "correct answer" point at the
  wrong translated option. `translations.spec.ts` checks this for every
  mission/step/checkpoint/comparison in all three language files against the
  real `MissionMeta` objects, not by convention; it was also verified live in
  the browser (answered translated checkpoints correctly in both Spanish and
  Ukrainian).
